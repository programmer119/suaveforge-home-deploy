DNS는 멀쩡했다. 배포는 패키지 하나 때문에 시작도 못 했다 — 재검수본

배포 실패를 보고 DNS부터 의심했지만 로그는 원격 연결보다 앞에서 멈췄다. Node가 필요한 모듈을 찾지 못해 배포 도구 자체가 시작되지 않았다. 장애명보다 실패 지점을 먼저 보는 사례다.

2026년 8월 27일Cases

“배포 실패.”

이 한 줄만 보면 DNS, 인증서, 방화벽, SSH, 서버까지 전부 의심하게 된다.

하지만 로그는 거기까지 가지도 않았다.

deploy-123.cjs가 ssh2를 불러오던 중 safer-buffer를 찾지 못했고 Node가 MODULE_NOT_FOUND로 종료됐다.

배포 도구 실행
     ↓
로컬 모듈 로딩  ← 여기서 종료
     ↓
SSH 연결
     ↓
원격 파일 반영
     ↓
공개 서비스 확인

DNS를 고칠 단계가 아니었다. 배포 도구가 원격 서버와 대화하기 전에 자기 실행에 필요한 재료부터 못 찾았다.

Node 공식 문서도 require()가 요청한 모듈을 찾지 못하면 MODULE_NOT_FOUND 오류를 낸다고 설명한다.

장애 이름보다 '마지막으로 성공한 단계'를 찾는다

“배포 실패”는 결과 이름이다. 원인은 아니다.

진단할 때는 뒤에서부터 상상하지 말고 로그가 실제로 어디까지 갔는지 본다.

1. 로컬 실행이 시작됐나
2. 필요한 모듈을 읽었나
3. 원격 연결을 시도했나
4. 인증이 됐나
5. 파일/프로세스가 바뀌었나
6. 외부에서 새 버전이 보이나

이 사례에서는 2번에서 멈췄다. 뒤 단계 설정을 만져도 첫 실패는 그대로 남는다.

뒤의 배포 로그에서는 누락된 실행 의존성을 deploy 영역에 갖춘 뒤 관련 검증이 통과했고, DNS는 DNS_ALREADY_OK 상태로 기록됐다.

“무엇이 실패했나?”보다 “어디까지 성공했나?”가 원인을 더 빨리 줄인다.

장애가 여러 층으로 보일수록 한 번에 다 고치려 하지 않는다. 첫 번째 실제 실패 지점부터 하나씩 내려가는 게 가장 짧다.
