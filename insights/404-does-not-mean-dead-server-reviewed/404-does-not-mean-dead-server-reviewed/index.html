404는 서버가 죽었다는 뜻이 아니다 — 재검수본

404가 보였다는 건 적어도 HTTP 응답을 돌려준 지점이 있다는 뜻이다. DNS·연결·TLS·라우트·앱을 한 덩어리로 보지 말고 실제로 어디까지 통과했는지 좁힌다.

2026년 8월 27일Insights

브라우저에 404 Not Found가 떴다.

여기서 바로 “서버가 죽었다”고 결론 내리면 진단 방향이 뒤집힌다.

MDN이 설명하는 404의 뜻은 간단하다. 서버가 요청한 리소스를 찾지 못했다는 HTTP 응답이다.

즉 화면에 404 응답이 보였다면 적어도 어떤 HTTP 응답 지점까지는 요청과 응답이 오갔다.

DNS 이름 해석
    ↓
서버까지 연결
    ↓
TLS/HTTPS 연결
    ↓
HTTP 응답
    ↓
요청한 경로 존재?  ← 404는 여기의 단서
    ↓
앱 내부 로직

다만 여기서도 과장하면 안 된다. 404를 누가 냈는지는 별도 확인해야 한다. 애플리케이션일 수도 있고, 앞단 웹서버나 프록시일 수도 있다.

404 하나로 서비스 전체를 판정하지 않는다

/가 404인데 /health는 200일 수 있다. 루트 경로를 만들지 않은 API 서버라면 이상하지 않다.

반대로 /health가 200이라고 로그인, 결제, DB 연결까지 전부 정상이라는 뜻도 아니다. health 경로가 확인하는 범위만 정상이라는 뜻이다.

GET /        → 404
GET /health  → 200

가능한 해석:
서버 전체 사망 ✕
경로별 상태를 더 확인해야 함 ✓

장애 진단은 층을 하나씩 벗긴다

DNS가 이름을 못 찾는지, TCP 연결이 안 되는지, TLS가 깨지는지, HTTP는 오는데 경로가 없는지, 경로는 있는데 앱에서 오류가 나는지는 서로 다른 실패다.

한꺼번에 “서버 문제”라고 부르면 손댈 곳이 너무 많아진다.

상태코드는 서비스 전체의 사망진단서가 아니라, 그 요청이 어디까지 갔는지 알려주는 단서다.

404를 받았다면 그 단서를 이용해 앞 단계 중 이미 통과한 것을 제외하는 것부터 시작한다.

MDN: 404 Not Found
