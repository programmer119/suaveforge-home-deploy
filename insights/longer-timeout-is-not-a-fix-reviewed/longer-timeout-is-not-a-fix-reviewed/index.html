타임아웃을 60초로 늘리면 문제가 해결된 걸까 — 재검수본

타임아웃은 느린 코드를 빠르게 만드는 설정이 아니다. 얼마나 기다린 뒤 이 요청을 실패로 취급할지 정하는 선이다.

AWS Well-Architected 가이드도 연결과 요청에 적절한 제한시간을 두고, 너무 높은 값은 자원을 오래 잡아두며 너무 낮은 값은 불필요한 재시도와 부하를 만들 수 있다고 설명한다.

하나의 숫자로 끝내지 않는다

먼저 어디서 시간이 쓰이는지 나눈다.

  • 서버에 연결 자체가 안 되는가
  • 연결은 됐는데 응답 처리가 오래 걸리는가
  • 원래 오래 걸려야 하는 작업인가
  • 실패 뒤 같은 요청을 다시 보내도 안전한가

예를 들어 파일 변환처럼 원래 오래 걸리는 작업을 3초에 잘라버리면 정상 작업을 실패로 만든다. 반대로 즉시 끝나야 할 조회가 매번 50초를 잡아먹는데 60초로 늘리면 장애를 늦게 발견한다.

재시도는 타임아웃의 자동 짝이 아니다

“끊겼으니 한 번 더”가 항상 안전한 것도 아니다.

뒤쪽 서버가 이미 느려진 상태라면 모든 클라이언트가 반복 요청을 던지면서 더 심하게 막을 수 있다. 결제나 생성 작업처럼 같은 요청이 두 번 실행되면 안 되는 작업은 중복 처리 방지도 함께 필요하다.
