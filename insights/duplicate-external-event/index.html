외부 서비스가 같은 이벤트를 다시 보내도 작업은 한 번만 실행해야 한다

외부 서비스는 응답을 받지 못하면 같은 이벤트를 다시 보낼 수 있고 두 요청이 거의 동시에 들어올 수도 있다. 고유한 이벤트 식별값을 기준으로, 동시에 들어온 요청까지 포함해 한 번만 처리되도록 해야 한다.

2026년 8월 31일Insights

결제사나 배송사 같은 외부 서비스는 응답을 받지 못하면 같은 이벤트를 다시 보낼 수 있다. 네트워크가 느리면 첫 요청을 처리하는 동안 같은 식별값을 가진 두 번째 요청이 들어오는 경우도 있다.

단순히 처리 여부를 조회한 뒤 작업을 시작하는 것만으로는 충분하지 않다. 두 요청이 동시에 같은 상태를 조회하면 둘 다 아직 처리되지 않았다고 판단할 수 있기 때문이다.

event_id = evt_42
1번째 요청: 처리 레코드 생성 성공 → 작업 실행
2번째 요청: 같은 event_id 생성 충돌 → 기존 처리 상태 확인

이런 경쟁을 막으려면 같은 이벤트 식별값에 대해 처리 권한을 한 요청만 얻도록 해야 한다. 예를 들어 데이터베이스에 이벤트 식별값을 UNIQUE로 묶고, INSERT 한 번으로 처리 권한을 선점할 수 있다.

같은 식별값이 이미 있다고 무조건 요청을 무시해서도 안 된다. 첫 처리자가 중간에 실패할 수 있으므로 처리 중·완료·실패 상태와 재시도 기준을 함께 두어야 한다.

DB 상태 변경처럼 하나의 트랜잭션에 묶을 수 있는 작업은 식별값 선점과 실제 변경을 같은 트랜잭션 안에서 처리하는 편이 안전하다. 외부 API 호출이나 알림 발송처럼 같은 트랜잭션에 묶기 어려운 작업은 별도의 고유 키나 발송 기록으로 중복 실행을 막아야 한다.

테스트도 순차 재전송만 해서는 부족하다. 같은 이벤트를 연달아 보내는 경우와 거의 동시에 두 번 보내는 경우를 모두 확인해야 한다.

같은 이벤트가 여러 번 들어와도 최종 결과는 한 번 처리한 것과 같아야 한다. 그래야 주문 상태가 두 번 바뀌거나 포인트·알림이 중복되는 일을 막을 수 있다.
