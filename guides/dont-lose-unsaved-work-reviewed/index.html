뒤로가기 한 번에 입력한 내용이 사라지면 안 된다 — 재검수본

긴 입력 화면에서 “저장 안 했으니 사용자 책임”으로 끝내면 안 된다. 이탈 경고는 마지막 안전망이고, 잃었을 때 비용이 큰 입력은 임시저장·자동저장까지 단계적으로 설계한다.

2026년 8월 27일Guides

10분 동안 입력했다.

뒤로가기를 한 번 눌렀다.

전부 사라졌다.

“저장 버튼을 안 눌렀잖아요”라고 말할 수는 있다. 하지만 긴 입력을 받는 서비스라면 아직 저장되지 않은 내용이 있다는 사실을 시스템도 알고 있다. 그걸 어떻게 다룰지가 제품 설계다.

입력 비용이 작다 ────────────── 입력 비용이 크다
검색 조건      짧은 메모      신청서·계약서·관리자 편집
그냥 이탈       경고            임시저장 / 자동저장

경고창은 마지막 안전망이다

브라우저의 beforeunload는 사용자가 페이지를 닫거나 새로고침하거나 다른 곳으로 이동하려 할 때 확인 대화를 띄우는 용도로 쓰인다.

하지만 MDN은 이 이벤트가 일부 환경, 특히 모바일에서 신뢰할 수 없는 경우가 있다고 설명한다. 중요한 입력을 지키는 유일한 장치로 두기 어렵다.

그래서 “떠나기 직전 경고”만 볼 게 아니라 작성 중에 얼마나 복구할 수 있게 해둘지를 같이 본다.

잃었을 때 비용으로 강도를 정한다

검색 필터 몇 개가 사라지는 것과 20분 작성한 계약서 초안이 사라지는 것은 같은 문제가 아니다.

다시 쓰는 비용 낮음  → 별도 보호 없음 또는 가벼운 경고
다시 쓰는 비용 중간  → 변경 감지 + 이탈 경고
다시 쓰는 비용 높음  → 임시저장/자동저장 + 복구 시점 표시

자동저장도 무조건 좋은 것은 아니다. 사용자가 확정하지 않은 값을 서버에 저장하면 안 되는 업무도 있고, 여러 사람이 동시에 편집하면 충돌 처리도 필요하다.

정답은 “자동저장 켜기”가 아니라 사용자가 잃을 수 있는 것의 크기와 데이터 성격을 보고 보호 수준을 정하는 것이다.

저장 여부를 화면에서도 읽을 수 있어야 한다

작성 중인 값이 저장됐는지, 마지막 저장이 언제였는지, 지금 변경사항이 남아 있는지 화면에서 알 수 있으면 사용자는 이탈 전에 판단할 수 있다.

저장 버튼이 있다는 것과, 사용자가 쓴 내용을 지켜주는 것은 같은 일이 아니다.
