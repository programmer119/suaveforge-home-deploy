결제 버튼을 두 번 눌러도 결제는 한 번만 되어야 한다 — 재검수본

느린 네트워크에서 사용자가 결제 버튼을 다시 누르는 건 정상 행동이다. 같은 결제 요청임을 서버가 알아보고 한 번만 처리하도록 해야 재시도가 사고가 되지 않는다.

2026년 8월 27일Guides

결제 버튼을 눌렀다. 아무 반응이 없는 것처럼 보인다.

한 번 더 누른다.

이 행동을 사용자 실수로 취급하면 설계가 약해진다. 첫 요청이 서버에 도착했는지, 결제가 끝났는지 화면에서 알 수 없을 때 다시 누르는 건 정상적인 행동이다.

사용자          서버
  |  결제 요청 A  |
  | ------------> |
  |   응답 유실   X
  |               |
  |  결제 요청 A  |
  | ------------> |
  |               |

여기서 서버가 두 번째 요청을 새 결제로 보면 사고가 난다.

같은 요청에는 같은 번호표를 붙인다

Stripe는 안전한 재시도를 위해 idempotency key를 지원한다. 이름은 어렵지만 뜻은 간단하다.

같은 작업인지 알아보는 번호표

첫 결제 요청에 ORDER-123-ATTEMPT-1 같은 고유한 번호표를 붙였다고 하자. 응답이 끊겨 같은 결제를 다시 보내더라도 서버는 번호표를 보고 “아까 그 작업”이라고 구분할 수 있다.

요청 A + 번호표 7F3A  → 결제 1회 실행
응답 끊김
요청 A + 번호표 7F3A  → 같은 결과 반환

Stripe 공식 문서도 같은 idempotency key로 요청을 재시도하면 같은 작업을 실수로 두 번 수행하지 않도록 설계할 수 있다고 설명한다.

버튼 잠금만으로는 부족하다

결제 버튼을 누른 뒤 잠깐 비활성화하는 것도 필요하다. 사용자가 연속 클릭하는 것을 줄여준다.

하지만 브라우저 새로고침, 앱 재실행, 네트워크 라이브러리의 자동 재시도처럼 화면 버튼 밖에서 같은 요청이 다시 나갈 수 있다. 그래서 최종 방어선은 서버 쪽에 있어야 한다.

재시도 가능 여부도 작업마다 다르다

조회 요청은 다시 보내도 보통 상태를 바꾸지 않는다. 결제·주문 생성·포인트 차감처럼 상태를 바꾸는 작업은 중복 실행이 사고가 된다.

따라서 “재시도 몇 번”부터 정하지 않는다.

이 요청이 두 번 실행돼도 안전한가?
        ↓ 아니오
같은 작업을 식별할 수 있는가?
        ↓ 예
같은 작업은 한 번만 처리

재시도는 예외 상황이 아니라 정상 사용 흐름이다. 사용자가 두 번 눌러도 돈은 한 번만 움직여야 한다.
