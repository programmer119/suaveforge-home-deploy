소셜 로그인 붙이기 전에 계정 흐름부터 그려야 한다 — 재검수본

Google·Kakao 버튼을 붙이는 것보다 먼저 “이 사람이 기존 사용자면?”, “처음 온 사람이면?”, “연결을 잃으면?”을 정해야 한다. 버튼 뒤의 계정 상태를 결정하는 짧은 흐름도.

2026년 8월 27일Guides

소셜 로그인 버튼은 입구다.

진짜 설계는 버튼을 누른 뒤 이 사람이 서비스 안에서 누구로 남는지부터 시작한다.

소셜 로그인 성공
      ↓
서비스 계정이 이미 있나?
   ┌──┴──┐
  예     아니오
  ↓        ↓
어떤 기준으로 연결?   새 계정을 만들까?
  ↓        ↓
연결 사실 안내      생성 사실 안내
      \      /
       복구 경로

먼저 네 상황만 정한다

  1. 같은 소셜 계정으로 이미 들어온 적이 있는 사람
  2. 이메일·전화번호 등 다른 방식의 기존 계정이 있는 사람
  3. 정말 처음 온 사람
  4. 소셜 연결을 잃거나 해제한 사람

여기서 필요한 건 OAuth 용어 시험이 아니다. 각 상황에서 계정이 하나로 남는지, 둘로 갈라지는지, 다시 들어올 길이 있는지를 정하는 일이다.

Google의 Streamlined Linking 문서도 프로필 정보를 받은 뒤 기존 계정 존재 여부를 확인하고, 기존 계정을 연결하거나 계정이 없을 때 생성하는 흐름을 구분한다.

자동 연결은 편하지만 위험한 질문을 남긴다

기존 계정을 찾았다고 해서 무조건 자동 연결하는 것이 항상 맞는 것은 아니다. 어떤 정보를 같은 사람의 계정이라고 믿을지, 추가 본인 확인이 필요한지 서비스마다 다르다.

그래서 구현 전에 최소한 이것은 답해야 한다.

  • 기존 계정을 무엇으로 찾을 것인가
  • 연결 전에 추가 확인이 필요한가
  • 처음 온 사용자는 로그인과 동시에 가입시킬 것인가
  • 가입이나 연결이 일어났다면 사용자에게 알려줄 것인가
  • 소셜 계정을 잃어도 다른 복구 수단이 남는가

편리함은 뒤의 복잡함을 없애는 게 아니다

소셜 로그인은 비밀번호를 줄여준다. 그렇다고 계정 생명주기까지 사라지는 건 아니다.

입구를 1클릭으로 줄였다면
↓
계정 생성 · 연결 · 해제 · 복구는
오히려 더 명확하게 설계해야 한다

입구만 매끈하고 계정이 안에서 둘로 갈라지면 소셜 로그인은 완성된 게 아니다.
